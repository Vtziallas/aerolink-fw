# Simulation Test: Command Replay Protection

Validates the Mission Agent's `ReplayGuard` (`onboard/mission-agent/src/replay_guard.h/.cpp`),
which closes the "stale/duplicate `command_id` rejection" gap `NETWORKING.md`
had flagged as deferred since the Mission Agent's original design. Anyone who
captures a `START_MISSION` or `RETURN_TO_LAUNCH` command on the wire must not
be able to replay it later and have the agent execute it again.

## SETUP

Unit-level coverage runs via the normal build/test targets, no simulation
infrastructure required:

- `cmake --build . --target mission_agent_tests` in `onboard/mission-agent/build/`.

Live format-compatibility verification (does the parser handle the *real*
backend's timestamp format, not just a unit test's approximation of it) reuses
the same four-process setup as `companion_service_restart.md`: `launch-px4-only.sh`,
`launch-agent-only.sh` (rebuilt with `ReplayGuard`), `launch-ground.sh`, the
`socat` relay, and the frontend dev server.

## ACTION

1. Run `mission_agent_tests` and confirm the `[replay_guard]` and
   `[command_validator]` test tags all pass.
2. Restart the Mission Agent with the `ReplayGuard`-enabled binary; through
   the frontend, upload and start one real mission.
3. Cross-check the backend log (`/tmp/backend_ground_net.log`) and PX4's own
   log (`/tmp/px4_sitl_aircraft_net.log`) to confirm the mission's real
   `command_id`/`timestamp` pair (a UUID4 and
   `datetime.now(timezone.utc).isoformat()`, generated by
   `mission_agent_client.py`) was accepted, not falsely rejected as stale or
   malformed.

## EXPECTED RESULT

- `ReplayGuard`'s own unit tests confirm: a fresh command is accepted; a
  repeated `command_id` within the 30s window is rejected
  (`"already processed"`); a timestamp older than the window, or more than
  the window into the future, is rejected (`"freshness window"`); a
  malformed timestamp is rejected (`"could not be parsed"`); both `Z` and
  `+HH:MM` timestamp suffixes are accepted (the real backend sends `+00:00`,
  not `Z`); a `command_id` is usable again once it has genuinely aged out of
  the window.
- `CommandValidator`'s own tests confirm the check is wired in at the right
  point: a command rejected for the wrong `aircraft_id` does not burn its
  `command_id` in the replay cache (the existing
  `"honors a non-default expected aircraft_id"` test depends on exactly this
  ordering), and two otherwise-valid commands sharing a `command_id` are
  correctly rejected on the second one.
- Live: the real mission's `POST /api/missions` and
  `POST /api/missions/current/start` both return `200 OK` (a validator
  rejection would have surfaced as `422`/`503` per `main.py`), and PX4's log
  shows a normal complete flight -- proving the real backend's timestamp
  format round-trips through the parser without a false rejection.

## PASS CRITERIA

- [x] Fresh, well-formed commands are accepted.
- [x] A repeated `command_id` within the freshness window is rejected.
- [x] A stale timestamp (older than the window) is rejected.
- [x] A timestamp too far in the future is rejected (not just too old).
- [x] A malformed timestamp is rejected (fail-closed, not silently accepted).
- [x] A command rejected for a different reason first (wrong `aircraft_id`)
      does not consume its `command_id`'s replay-cache slot.
- [x] The real backend's actual `command_id`/timestamp format is accepted
      live, not just a unit test's approximation of it.

## Design notes worth keeping

- **Cache lifetime is in-memory only; it resets on a Mission Agent restart.**
  This is a deliberate scope decision, not an oversight: no persistence layer
  exists anywhere else in this codebase, and the 30s timestamp-freshness
  check bounds the replay window on its own even immediately after a
  restart, since a timestamp old enough to have been captured before the
  restart will already fail the staleness check regardless of whether the
  seen-`command_id` cache remembers it.
- **Ordering matters:** the replay check runs *after* the existing
  `aircraft_id` identity check, matching `NETWORKING.md`'s own layer
  ordering (application-layer auth before replay protection). A command
  rejected for identity never reaches the replay cache, so a misdirected
  command doesn't burn a legitimate future `command_id`.
- **Fail-closed on malformed timestamps**, consistent with this codebase's
  existing posture elsewhere (e.g. `CommandValidator::check_position_settled`
  rejecting with a clear reason rather than guessing at an unclear PX4
  state).
- **Not covered by this pass:** command signing / origin authentication.
  `ReplayGuard` stops a captured command from being *replayed*, but nothing
  yet stops a party with tunnel access from *forging* a fresh command with a
  current timestamp and an unused `command_id` -- that's the "command
  signing" layer `NETWORKING.md` still lists as design-only.
