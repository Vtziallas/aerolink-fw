The project is called:

# AeroLink-FW

A fixed-wing autonomous UAV that receives high-level mission instructions from a PC through a cellular 4G/LTE connection and executes those missions autonomously using an onboard autopilot.

The project is strictly intended for civilian engineering education, research, simulation, and lawful flight testing.

It must NOT include weapons, payload-dropping systems, targeting capabilities, covert surveillance functionality, deliberate avoidance of aviation authorities, disabling safety mechanisms, or instructions for violating aviation regulations.

For real-world testing, design everything around lawful, controlled, VLOS test flights in permitted airspace. Long-distance/BVLOS behavior should initially be demonstrated entirely in simulation unless the appropriate aviation authorization exists.

# 2. PRIMARY DEMONSTRATION

The eventual portfolio demonstration should look approximately like this:

1. Operator opens my custom web-based Ground Control Station.

2. UAV appears online.

3. The dashboard shows:

   * aircraft location
   * GPS status
   * altitude
   * airspeed
   * groundspeed
   * heading
   * battery voltage
   * flight mode
   * armed/disarmed state
   * LTE signal quality
   * latency
   * mission progress
   * link status
   * warnings/failsafes

4. Operator selects points on a map.

For example:

HOME → A → B → C → HOME

5. Ground station validates the mission.

6. Operator uploads the mission.

7. Aircraft confirms that the complete mission has been received.

8. The aircraft performs the mission using its onboard autopilot.

9. Telemetry is streamed back through 4G.

10. The dashboard displays the flight live.

11. If cellular connectivity disappears, the aircraft DOES NOT crash and DOES NOT depend on continuous PC commands.

Instead, an onboard safety state machine performs a configured response such as:

* continue an already validated mission for a limited period
* loiter
* return-to-launch
* transition to a safe landing procedure

depending on the phase of flight and configured policy.

12. Once connectivity returns, telemetry synchronizes again.

The 4G connection must NOT be flight-critical.

The aircraft should be capable of maintaining stable flight without Internet connectivity.

The autopilot must live on the aircraft.

High-frequency control loops must NEVER depend on:

* cellular latency
* a cloud server
* the browser
* Wi-Fi
* the Internet
* a remote database

The architecture should follow this separation:

LOW-LEVEL REAL-TIME:

PX4 Flight Controller

HIGH-LEVEL ONBOARD:

Linux Companion Computer

Responsible for:

* LTE connectivity

* command validation
* optional advanced autonomy later

REMOTE:

Ground-control PC

Responsible for:

* mission creation

# 4. PROPOSED TECHNOLOGY STACK

Evaluate this stack and improve it where appropriate.

## Flight controller

PX4 Autopilot on a Pixhawk-compatible flight controller.

Use a CURRENT STABLE PX4 release rather than blindly using development/main.

The UAV is FIXED-WING, not quadcopter.

---

## Companion computer

Initially:

Raspberry Pi / Compute Module class Linux computer

or another lightweight Linux SBC if technically preferable.

The companion computer will communicate with the flight controller through an appropriate supported interface.

It will run:

* Linux
* mission communication service
* telemetry service
* network monitoring
* MAVSDK/MAVLink integration
* logging
* secure networking
* systemd services

Eventually it may run:

* ROS 2
* OpenCV
* AI inference
* computer vision

but DO NOT introduce those unnecessarily in version 1.

---

## Cellular connectivity

A 4G/LTE modem with SIM card connected to the companion computer.

Important:

The LTE modem should connect to the Linux companion computer rather than directly becoming part of the flight-control loop.

Design for:

* NAT
* dynamic cellular IP addresses
* reconnects
* temporary loss of connectivity
* variable latency
* variable bandwidth
* packet loss

Do not assume that the UAV receives a publicly reachable IP address.
